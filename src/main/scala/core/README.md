## 设计原则

### "三权分立"的架构地位

在处理器设计中, `ISA`(规范), `Micro-Architecture`(机制) 和 `Implementation`(实现) 是三个平等的支柱

* `isa`: 宪法。
* `uarch`: 法律与协议。
* `frontend/backend`: 行政机构。

### 为什么不把 `isa` 和 `uarch` 放到一起?

#### 1. 增加引用深度 (The Import Tax)

代码是用来看的, 也是用来写的.

* 现在的写法: `import core.isa._`, `import core.uarch._`.
* 合并后的写法: `import core.specs.isa._`, `import core.specs.uarch._`.

这多出来的一层目录, 除了增加键盘敲击次数, 并没有提供额外的语义信息.
`core` 本身就已经是一个足够明确的命名空间了.

#### 2. 语义混淆 (Semantic Blur)

一旦建立了一个父目录(比如 `core.defs`),
根据热力学第二定律(熵增), 你或者协作者很快就会往这个父目录里直接塞东西.

比如塞一个 `Consts.scala`

它是属于 `ISA` 的常量? 还是微架构的常量?

没人在乎了, 反正都在 `defs` 里. 最后又变成了一团乱麻.
保持 `isa` 和 `uarch` 独立, 强迫你在新建文件时必须做出选择:
"这是 RISC-V 规定的, 还是我设计的?"

#### 3. "三权分立"的架构地位

把 `isa` 和 `uarch` 降级到一个子文件夹里, 掩盖了它们作为架构基石的重要性.

### `isa` 和 `uarch` 之间的关系

| 特性 | core.isa | core.uarch |
| --------------- | --------------- | --------------- |
| 定义来源 | 外部输入 (RISC-V Handbook) | 内部输出 (Designer's Mind) |
| 稳定性 | 极高 (十年不变) | 极低 (随性能调优而变) |
| 依赖方向 | 被所有人查阅 | 被模块间通信使用 |
| 本质 | The "What" (要做什么) | The "How" (怎么传信号) |

正因为变化频率和来源完全不同, 把它们物理隔离在不同的一级目录下, 有助于你在版本控制(Git)中清晰地看到:

* "哦，这次 `commit` 改了 `uarch`，看来是调整了流水线控制信号。"
* "哦，这次 `commit` 改了 `isa`，看来是支持了新的 `RISC-V` 扩展。"
